2. MAIN PRODUCTION REVIEW
=========================

EXECUTIVE ASSESSMENT
--------------------
The highest-value improvements are user/data isolation, deployment-artifact
privacy, document-version integrity, recoverable ingestion, and request failure
handling. These are supported by the current implementation rather than README
claims.

All five findings below are defects or missing production controls, not cosmetic
refactors. Security exposure depends on who can access the deployment and
whether stored data is private; those conditions were not verified.

ACTUAL ARCHITECTURE AND DATA FLOW
--------------------------------
- Requests: app.py launches Gradio and creates shared Gemini, S3, Chroma, and
  memory objects. Browser conversation history uses gr.State, but persistent
  memory and the document collection are application-wide.
- Agent: agent.py executes a synchronous LangGraph loop. Gemini can request
  searches, which run through a five-worker thread pool. Optional query
  decomposition precedes generation; an optional faithfulness check follows it.
- Retrieval: Standard search queries Chroma. Hybrid search combines Chroma and
  an in-memory BM25 index through reciprocal rank fusion, with optional
  cross-encoder reranking.
- Visual citations: Search results trigger S3 PDF lookup, rendering/cropping,
  image caching, and one-hour presigned URLs.
- Ingestion: Gradio uploads PDFs to S3; S3 invokes the ADE Lambda; Lambda writes
  Markdown, grounding JSON, and individual chunks; the web handler polls S3
  and indexes chunks into local persistent Chroma.
- Persistence/deployment: Conversation memory is a JSON file. Compose mounts
  memory and Chroma from the host. Docker copies the build context; the Hugging
  Face deployment script uploads the working directory.
- Evaluation: Separate scripts generate datasets, run agent variants, and
  calculate retrieval/faithfulness metrics. These are not runtime protection
  mechanisms.

FINDING 1 — P0: ISOLATE PERSISTENT MEMORY AND DOCUMENT ACCESS BETWEEN USERS
------------------------------------------------------------------------
Classification: Verified isolation defect; security impact when independent
users access the application.

Evidence:
- app.py:598–615 initializes and passes one shared memory object and collection
  into the UI.
- app.py:292–296 makes conversation history session-local, but does not isolate
  persistent memory.
- app.py:262–270 updates shared memory and saves it to the same file.
- gemini_helpers.py:380–395 inserts remembered preferences, facts, and the last
  session summary into subsequent prompts.
- app.py:127–130,356–357 displays the last saved session summary.
- app.py:393–411,617–623 exposes document upload and launches without
  application authentication.
- gemini_helpers.py:277–281 and hybrid_search.py:54–58 query the collection
  without ownership filters.

Trigger and impact:
User A saves a conversation; user B's subsequent request receives A's remembered
information in its system prompt and potentially in the memory panel. Uploaded
documents also become searchable by other users. Authentication alone would not
correct these shared-state leaks.

Memory persistence additionally uses a direct truncating write
(gemini_helpers.py:360–361), with no locking or atomic replacement. Concurrent
saves or interrupted writes can lose or corrupt persistent state.

Practical fix:
Introduce an authenticated user/tenant identity and carry it through memory
loading, saving, uploads, and retrieval. Store memory per identity and enforce
document ownership filters server-side. Use atomic file replacement and
synchronized updates if retaining JSON storage. For a deliberately public demo,
disable personal persistent memory and restrict knowledge-base mutation to an
administrator.

Uncertainty:
External authentication and the intended trust boundary were not inspected.
Shared-memory behavior remains a defect even behind authentication.

FINDING 2 — P0: PREVENT RUNTIME/PRIVATE DATA FROM ENTERING DEPLOYMENT ARTIFACTS
---------------------------------------------------------------------------
Classification: Verified packaging-control omission; disclosure is conditional
on private data being present.

Evidence:
- deploy.py:11–15 uploads folder_path="." with exclusions that do not explicitly
  cover conversation memory, Chroma, source documents, parsed chunks, or
  notebooks.
- Dockerfile:24–25 uses COPY . .
- .dockerignore:37–45 excludes memory and some data directories, but does not
  exclude chroma_db/, documents/, or document_chunks/.
- .gitignore:2–6,14–15 identifies Chroma, generated archives, and conversation
  memory as local/generated state.

Trigger and impact:
Build or deploy from a populated developer workspace. The Docker path can bake
document text and metadata from Chroma into an image. The Hugging Face path
lacks an explicit application-artifact boundary, allowing local data to become
deployment candidates. Git exclusions are not a sufficient confidentiality
control for these paths.

Practical fix:
Package from a clean staging directory using an explicit application-file
allowlist. Exclude databases, conversation memory, source/parsed documents,
notebook outputs, environment variants, and generated archives. Add an
artifact-content check before publication.

Uncertainty:
No image or upload was created, and no actual disclosure is asserted. Effective
Hugging Face SDK filtering was not exercised; the Docker exclusion gap is
directly visible in the repository.

FINDING 3 — P0: PRESERVE IMMUTABLE DOCUMENT VERSIONS ACROSS PARSING,
                INDEXING, AND CITATIONS
-----------------------------------------------------------------
Classification: Verified correctness/data-integrity bug.

Evidence:
- upload_handler.py:24–32 derives input and output identities from the filename
  and overwrites the same S3 input key.
- ade_s3_handler.py:105–118 skips parsing when previous Markdown exists;
  config.py:38–39 defaults reprocessing to false.
- upload_handler.py:39–44 accepts any existing grounding object for that
  filename.
- gemini_helpers.py:195–200,224–230 skips existing chunk IDs and adds new records
  without replacing the old document.
- ade_s3_handler.py:285–289 stores only the filename stem as source identity.
- agent.py:139–143 reconstructs the PDF key from that stem.
- visual_grounding_helper.py:91–101 reuses cached images without checking the
  source version.
- hybrid_search.py:23–25,43–44 caches BM25 indefinitely by collection name;
  indexing does not invalidate it.

Trigger and impact:
Upload a changed PDF with the same filename. The PDF can be replaced while old
parsing output and old indexed text remain active. Answers can cite stale text
against a different PDF. Forced reprocessing does not reconcile prior chunks,
and lexical retrieval remains stale after uploads.

Filename-prefix selection also permits unintended mixing: the report_ prefix
in upload_handler.py:58–62 matches chunks for both report.pdf and
report_appendix.pdf.

Practical fix:
Give each document version an immutable identity based on owner, full source
key, and content hash or S3 version. Preserve that identity in chunk metadata
and citation/image keys. Index the new version completely, activate it
explicitly, then retire the prior version. Load exact chunk keys from a manifest
rather than filename prefixes. Version or invalidate the BM25 cache after
successful activation.

FINDING 4 — P1: MAKE INGESTION COMPLETION TRUTHFUL, RECOVERABLE, AND RETRY-SAFE
---------------------------------------------------------------------------
Classification: Verified production-reliability bugs.

Evidence:
- ade_s3_handler.py:141–146 writes Markdown before the rest of the artifacts.
- ade_s3_handler.py:249–256 publishes grounding JSON before writing individual
  chunks at 259–297.
- upload_handler.py:39–55 treats grounding existence plus a fixed five-second
  sleep as completion.
- ade_s3_handler.py:305–312 catches grounding/chunk failures and still records
  success.
- ade_s3_handler.py:316–325 catches processing failures and returns normally.
- upload_handler.py:50–52,65–73 can time out or index zero chunks and still end
  with an overall success message.
- gemini_helpers.py:129–138 suppresses individual chunk-loading failures.

Trigger and impact:
Chunk publication takes longer than five seconds, an S3 write fails, or Lambda
stops after writing Markdown. The UI can permanently index only part of a
document. A subsequent attempt can skip the incomplete document because
Markdown exists.

Caught failures do not signal a failed asynchronous Lambda invocation, so
Lambda's function-error retry behavior is not activated. Users receive success
messages while content is missing.

Practical fix:
Write version-specific artifacts, validate their IDs/counts, and publish a
completion manifest last. Treat that manifest, not Markdown or grounding
existence, as the idempotency/completion marker. Distinguish missing objects from
authorization and transient failures. Propagate failures, configure a failure
destination and alarms, and report accurate per-file outcomes. Enable retries
only after incomplete attempts can safely resume or restart.

FINDING 5 — P1: BOUND PROVIDER RETRIES AND PRESERVE CONVERSATION STATE
                TRANSACTIONALLY
------------------------------------------------------------------
Classification: Verified request-reliability defects; concurrent router failures
depend on scheduling.

Evidence:
- llm_router.py:73–77,107–111 retries every APIError up to six times, although
  rotation is limited to selected status codes.
- llm_router.py:25–28 contains duplicate primary fallback entries.
- llm_router.py:31–32,50–67,85–92 stores and mutates routing indices globally
  without synchronization.
- app.py:598 shares that router; app.py:616 permits concurrent handlers.
- agent.py:459–465,304–305,351–353 mutates supplied conversation history
  throughout a turn.
- app.py:229–232 attempts rollback by popping only its last element.

Trigger and impact:
A permanent API error receives unnecessary retries and backoff. Concurrent
requests can alter one another's routing choices; a context switch between
incrementing and normalizing a key index can expose an out-of-range index.

If generation fails after an earlier tool cycle, popping one history entry does
not remove the failed turn. It can leave an unmatched tool call or other partial
messages, contaminating the next request and potentially causing further
provider errors.

Practical fix:
Keep retry selection request-local, with synchronized shared cooldown
bookkeeping if needed. Deduplicate fallback models, classify retryable errors,
use jitter/Retry-After, and enforce an end-to-end deadline. Execute each agent
turn against a working history copy and commit it only on success. Validate
empty/blocked provider responses before dereferencing response.candidates[0].

RECOMMENDED IMPLEMENTATION ORDER
--------------------------------
1. Close runtime privacy boundaries: isolate memory, authorize retrieval, and
   restrict uploads.
2. Close artifact privacy boundaries: deploy only allowlisted application files.
3. Establish immutable document identity: reconcile index versions, citations,
   and retrieval caches.
4. Add manifest-based completion and recovery: then enable retries and accurate
   failure reporting.
5. Make requests bounded and transactional: correct router retries/concurrency
   and history rollback.

Add focused regression tests alongside each fix, especially cross-user
isolation, same-name replacement, interrupted chunk publication, and provider
failure after a tool call.

EXECUTIVE ASSESSMENT
--------------------
The ingestion path has several verified correctness and reliability defects:
replaced documents can retain old searchable content, uploads can index
incomplete output, Lambda failures are acknowledged as successful invocations,
and nested documents lose their full identity. Deployment helpers also overwrite
existing S3 notification configuration and can produce contaminated ZIP
artifacts.

Two P0 security issues are conditional on deployment context: the web application
exposes shared document-management operations without application
authentication, and deployment packaging does not consistently exclude local
private data.

This was a read-only static analysis. The subagent did not execute application
initialization, tests, builds, package installation, deployment commands, or
network operations. It did not read .env, memory.json, credentials, private
documents, chunk data, or notebook contents/outputs.

Severity:
- P0: security or serious data-integrity exposure
- P1: production reliability
- P2: performance/scalability

ARCHITECTURE AND DATA FLOW
--------------------------
1. Web application: app.py initializes one Gemini router, S3 client, persistent
   Chroma collection, and memory object for the application.
2. Upload: upload_handler.py uploads each file to input/documents/<basename>.
3. Asynchronous parsing: an S3 object-created notification invokes
   ade_s3_handler.py.
4. Lambda output: the handler downloads the PDF into /tmp, calls LandingAI ADE,
   then writes Markdown, aggregate grounding JSON, and individual chunk JSON
   objects.
5. Completion detection: the web upload handler polls for grounding JSON, waits
   another five seconds, downloads matching chunk objects, and adds them to
   local Chroma.
6. Retrieval: Chroma vector retrieval can be combined with a cached BM25 index
   and a lazily loaded cross-encoder.
7. Visual citations: source PDFs are located by a reconstructed filename,
   cropped, cached in S3, and exposed using presigned URLs.
8. Infrastructure: lambda_helpers.py imperatively creates/reuses IAM roles,
   builds ZIPs, deploys Lambda, and replaces S3 notification configuration.
9. Application deployment: Docker uses requirements-prod.txt; the Hugging Face
   upload script uploads the working directory. CI installs requirements.txt,
   not the Docker production dependency set.

There is no durable ingestion-job record or manifest connecting an upload
version to a complete, validated set of indexed chunks.

VERIFIED FINDINGS
-----------------

SUBAGENT FINDING 1 — P0: SHARED DOCUMENT OPERATIONS ARE EXPOSED WITHOUT
                         APPLICATION AUTHENTICATION
----------------------------------------------------------------------
Evidence:
- app.py:598–615: one collection, bucket, and memory object are supplied to UI.
- app.py:393–411: upload/index action is exposed directly through the UI.
- app.py:616–623: launch binds to 0.0.0.0, supplies no authentication, and
  disables strict CORS.
- docker-compose.yml:9–10: port is published without a loopback-only binding.
- upload_handler.py:27–29: uploads write to the shared bucket namespace.

Trigger:
The service is reachable by an untrusted user without an external authentication
layer.

Impact:
That user can upload documents into the shared knowledge base, overwrite a known
filename, poison retrieval content, and consume S3, Lambda, and ADE resources.
Retrieval has no per-user collection or authorization filter, so a shared
deployment does not isolate uploaded documents between users.

Practical fix:
Require authentication and authorization for upload and retrieval; namespace
documents by owner/tenant; enforce tenant filters server-side; restrict local
Compose publishing to 127.0.0.1 if public access is unnecessary. Re-enable strict
CORS unless there is a justified requirement.

Boundary:
Application-level omission is verified. External proxy authentication, Space
visibility, firewall rules, and intended trust boundaries were not inspected.

SUBAGENT FINDING 2 — P0: DEPLOYMENT PACKAGING CAN INCLUDE PRIVATE LOCAL STATE
--------------------------------------------------------------------------
Evidence:
- deploy.py:11–15: uploads folder_path="."; explicit exclusions do not cover
  memory.json, chroma_db/, input/, output/, or generated Lambda ZIPs.
- Dockerfile:24–25: copies remaining build context into the image.
- .dockerignore:37–45: excludes some private state, but not chroma_db/ or
  ade_lambda.zip.
- .gitignore:2–6,14–15: identifies Chroma, the Lambda ZIP, and conversation
  memory as local/generated state.

Trigger:
Deployment runs from a working directory containing excluded-from-Git private
state, or a Docker build includes a populated local Chroma database.

Impact:
Document text and metadata may be copied into a remotely hosted repository or
container image. A generated Lambda ZIP can also unintentionally redistribute
packaged local artifacts. A Git exclusion is not a sufficient deployment
confidentiality control.

Practical fix:
Deploy from a clean staging directory using an explicit source-file allowlist.
Exclude all databases, conversation memory, document directories, generated
archives, environment-file variants, and credential artifacts in every
deployment path. Inspect artifact contents before upload/build publication.

Boundary:
Packaging omissions are verified; private files were not inspected and no
upload was executed, so actual disclosure is not claimed. Effective Hugging
Face SDK filtering was not executed.

SUBAGENT FINDING 3 — P1: REPLACING A PDF CAN PERMANENTLY RETAIN THE OLD
                         PARSED AND INDEXED DOCUMENT
----------------------------------------------------------------------
Evidence:
- upload_handler.py:24–32: input/output identities depend only on filename/stem.
- ade_s3_handler.py:105–121: Markdown existence causes parsing to be skipped.
- config.py:38–39: reprocessing defaults to false.
- upload_handler.py:39–44,58–69: any existing grounding object is accepted,
  then matching chunks are indexed with skip_existing=True.
- gemini_helpers.py:195–200,224–230: existing IDs are skipped; indexing uses
  add, not replacement.

Trigger:
Upload a changed PDF with the same filename.

Impact:
The source PDF is overwritten, but Lambda can skip processing and the UI can
immediately consume previous grounding/chunks. Search returns old text while
citation generation may use the new PDF. Even forced reprocessing does not
remove previous S3 chunks or previous indexed records.

Practical fix:
Give each document version an immutable ID based on owner, full source key,
and content hash/version. Process and index that version, then atomically
activate it. Replace/delete prior version records explicitly. Cache visual
citations by source version too.

SUBAGENT FINDING 4 — P1: GROUNDING JSON IS PUBLISHED BEFORE CHUNKS, SO
                         UPLOAD COMPLETION RACES INDEXING
-------------------------------------------------------------------
Evidence:
- ade_s3_handler.py:249–256: grounding JSON is written first.
- ade_s3_handler.py:259–297: individual chunks are written afterward,
  sequentially.
- upload_handler.py:39–55: grounding existence is treated as completion,
  followed by a fixed five-second delay.
- upload_handler.py:58–71: whatever chunks currently exist are indexed,
  then success is reported.

Trigger:
Chunk creation takes more than five seconds after grounding publication, or
Lambda fails partway through chunk writes.

Impact:
Only a subset of chunks is indexed. There is no later reconciliation in this
path, so missing content can remain missing indefinitely.

Practical fix:
Write an immutable chunk set, validate its count/IDs, and publish a completion
manifest last. The UI should wait for the manifest for the exact uploaded
version and verify the listed objects before indexing. This is an application
commit-order problem, not a reason to add more arbitrary S3 sleeps.

SUBAGENT FINDING 5 — P1: LAMBDA SWALLOWS FAILURES, DEFEATING ASYNCHRONOUS
                         ERROR RETRIES
----------------------------------------------------------------------
Evidence:
- ade_s3_handler.py:305–312: grounding/chunk-write failures are caught and
  the document is still marked "success".
- ade_s3_handler.py:316–325: outer document failures are collected, but the
  invocation returns normally with "status": "ok".

Trigger:
ADE fails, input retrieval fails, or S3 output writes fail.

Impact:
AWS Lambda sees a successful invocation, not a failed asynchronous invocation.
Merely including "failed" in a returned JSON object does not activate Lambda's
error retry/failure-destination behavior. Missing or partially processed
documents are therefore silently acknowledged.

Practical fix:
Propagate invocation failures or move to an SQS-backed worker with explicit
item-level retry semantics. Make processing idempotent before enabling retries,
and configure a failure destination plus alarms.

SUBAGENT FINDING 6 — P1: MARKDOWN EXISTENCE PERMANENTLY "COMMITS"
                         INCOMPLETE INGESTION
---------------------------------------------------------------
Evidence:
- ade_s3_handler.py:105–118: Markdown existence is the processed-state check.
- ade_s3_handler.py:141–146: Markdown is written before grounding/chunks.
- ade_s3_handler.py:305–306: failures producing remaining artifacts are
  swallowed.

Trigger:
Markdown succeeds, but a later operation fails or Lambda times out.

Impact:
A subsequent event or manual retry skips the document despite missing chunks.
Fixing failure propagation alone would not repair this state: retries would
still hit the Markdown skip.

Practical fix:
Use a validated, version-specific completion manifest as the idempotency check.
A Markdown object must not represent completed ingestion.

SUBAGENT FINDING 7 — P1: FULL DOCUMENT IDENTITY IS LOST FOR NESTED PATHS;
                         SOME CHUNK SETS COLLIDE
----------------------------------------------------------------------
Evidence:
- ade_s3_handler.py:83–103: Markdown preserves input directory structure.
- ade_s3_handler.py:150–169: grounding preserves the deeper relative path.
- ade_s3_handler.py:285–289: chunk metadata retains only the filename stem;
  chunk keys omit deeper subdirectories.
- agent.py:139–143: citation lookup reconstructs only
  input/documents/<stem>.pdf.

Trigger:
Ingest input/documents/team-a/report.pdf and
input/documents/team-b/report.pdf, or documents outside input/documents/.

Impact:
Nested documents are flattened into a common chunk namespace and lose their
source identity. Depending on ADE chunk IDs, objects can overwrite each other
or distinct chunk sets can be mixed. Citation lookup either fails or selects
a different same-stem PDF.

Practical fix:
Store the exact source S3 key and immutable document/version ID in every chunk.
Preserve the full hierarchy or use a document-ID directory for chunks. Citation
generation should use stored source identity, not filename reconstruction.

SUBAGENT FINDING 8 — P1: UPLOAD PREFIX SELECTION CAN INCLUDE OTHER DOCUMENTS
-------------------------------------------------------------------------
Evidence:
- upload_handler.py:58–62: selects chunks with <stem>_.
- ade_s3_handler.py:289: object names concatenate stem and chunk ID with the
  same separator.
- gemini_helpers.py:122–134: every matching JSON object is accepted.

Trigger:
Upload report.pdf when report_appendix.pdf has already produced chunks.

Impact:
The prefix report_ matches both documents' chunk objects. Indexing can ingest
unrelated content and misleadingly attribute the operation to the uploaded
file.

Practical fix:
Use a delimiter-bounded document directory, such as
chunks/<document-id>/<version>/, and preferably enumerate exact chunk keys
from a manifest.

SUBAGENT FINDING 9 — P1: LAMBDA IMPORTS DEPEND ON AN UNRELATED GEMINI KEY
                         AND CAN LEAVE CONFIGURATION UNDEFINED
----------------------------------------------------------------------
Evidence:
- config.py:19: Gemini API key is always required.
- config.py:59–65: configuration failure is caught without creating settings
  or re-raising.
- ade_s3_handler.py:17,24–30: Lambda imports and immediately consumes settings.
- lambda_helpers.py:12: deployment helpers have the same import dependency.

Trigger:
Configure the ADE Lambda with its required ADE/AWS settings, but no Gemini key.

Impact:
Import fails because settings was never assigned. The ADE worker cannot start
even though its parsing path does not use Gemini. Missing ADE configuration is
also not validated by Config, because the ADE key is optional.

Practical fix:
Split settings by service responsibility, validate only each service's actual
requirements, and fail explicitly on invalid configuration. Avoid constructing
SDK clients before configuration validation.

SUBAGENT FINDING 10 — P1: S3 TRIGGER SETUP DELETES UNRELATED BUCKET
                          NOTIFICATION INTEGRATIONS
----------------------------------------------------------------
Evidence:
- lambda_helpers.py:296–309: calls put_bucket_notification_configuration with
  only one Lambda configuration.

Trigger:
Run setup on a bucket already configured with other Lambda, SNS, SQS, or
EventBridge notification settings.

Impact:
The supplied notification document replaces the bucket's existing
configuration. Other consumers can stop receiving events.

Practical fix:
Read existing configuration, preserve unrelated entries, and update a stable
ID for this trigger, or manage the complete notification document through one
infrastructure owner. Guard against concurrent configuration changes.

SUBAGENT FINDING 11 — P1: EXISTING EXECUTION ROLES ARE REUSED WITHOUT
                          RECONCILING REQUIRED PERMISSIONS
------------------------------------------------------------------
Evidence:
- lambda_helpers.py:49–77: logging and bucket policies are installed only after
  new-role creation.
- lambda_helpers.py:82–85: an existing role is simply fetched and reused.
- lambda_helpers.py:66–67: bucket permissions depend on current settings.

Trigger:
Reuse a role after changing the bucket, recover from partially completed setup,
or use a pre-existing role lacking required policies.

Impact:
Deployment reports role reuse, but Lambda can lack S3 or logging access. It can
also retain obsolete broader permissions.

Practical fix:
Reconcile the trust policy, managed logging policy, and desired inline policy
on every run. Scope object read/write permissions to input/output prefixes
where possible.

SUBAGENT FINDING 12 — P1: ZIP PACKAGING CAN RETAIN DELETED FILES AND
                          SILENTLY TOLERATE FAILED BUILD STEPS
-----------------------------------------------------------------
Evidence:
- lambda_helpers.py:110–112: removes package directory, but not previous output
  archive.
- lambda_helpers.py:166–175: source copying and ZIP creation do not check exit
  status.
- lambda_helpers.py:180–184: an existing ZIP's size can be reported as
  successful output.

Trigger:
Rebuild an existing archive after removing/renaming dependencies or source
files, or encounter a failed copy/archive command.

Impact:
zip -r updates an existing archive; omitted old members need not be deleted.
A stale file can survive deployment, or a failed build can return an older ZIP
as if it were newly built.

Practical fix:
Build in a unique temporary directory, create a brand-new archive, check all
subprocess results, validate required modules and archive members, then
atomically publish the artifact. Use argument arrays rather than interpolated
shell commands.

SUBAGENT FINDING 13 — P1: LAMBDA DEPLOYMENT USES FIXED SLEEPS INSTEAD OF
                          READINESS CHECKS AND IGNORES ROLE/ARCHITECTURE
                          CHANGES
----------------------------------------------------------------------
Evidence:
- lambda_helpers.py:232–247: code update is followed by a ten-second sleep and
  immediate configuration update.
- lambda_helpers.py:213–223: role and architecture are applied on creation.
- lambda_helpers.py:241–248: update does not apply either role or architecture.
- lambda_helpers.py:114–140: package dependencies always target Python
  3.12/Linux x86-64.

Trigger:
An update lasts more than ten seconds; desired execution role changes; an
existing function is ARM64; or a caller requests a runtime/architecture
different from the hardcoded wheel target.

Impact:
Updates can encounter conflicts or leave the function using the wrong role.
Binary wheels can be incompatible with actual function runtime/architecture.

Practical fix:
Use Lambda waiters and inspect update status after code and configuration
changes. Reconcile role and architecture. Derive package targets from desired
function configuration and reject unsupported combinations.

SUBAGENT FINDING 14 — P1: UPLOAD FAILURES AND EMPTY/PARTIAL INDEXING ARE
                          REPORTED AS OVERALL SUCCESS
---------------------------------------------------------------------
Evidence:
- upload_handler.py:45–51: all polling exceptions are treated as "not yet
  processed"; timeout continues to the next file.
- upload_handler.py:65–73: zero chunks can still result in "Done indexing" and
  the unconditional final success message.
- gemini_helpers.py:129–138: individual chunk download/JSON failures are
  suppressed.
- lambda_helpers.py:344–359: synchronous invocation success is judged by HTTP
  status alone, without checking Lambda's FunctionError.

Trigger:
Access is denied during polling, parsing times out, chunks are
malformed/unreadable, ADE returns no chunks, or a synchronous Lambda invocation
returns a function error with HTTP 200.

Impact:
Operators/users receive misleading success signals while the knowledge base
is incomplete or unchanged. Access-denied errors can waste the entire polling
window.

Practical fix:
Distinguish not-found from permission/transient failures; propagate partial
ingestion failures; validate expected counts; return per-file outcomes and an
accurate aggregate summary. Check FunctionError on synchronous invocations.

SUBAGENT FINDING 15 — P1: BM25 REMAINS STALE AFTER DOCUMENT UPLOADS
----------------------------------------------------------------
Evidence:
- hybrid_search.py:23–25,43–44: cache is keyed by collection name and returned
  indefinitely.
- upload_handler.py:65–70: ingestion mutates collection without invalidating
  the cache.
- app.py:137,326–333: hybrid retrieval is the default UI mode.

Trigger:
Run a hybrid search, then upload/index new documents in the same process.

Impact:
New documents participate in dense search but not lexical retrieval until
restart. A same-name collection from another database can also reuse the wrong
lexical cache within a process.

Practical fix:
Key the cache by database/collection identity and an ingestion generation.
Invalidate or rebuild it after successful index mutation, with synchronization
around concurrent readers/builders.

SUBAGENT FINDING 16 — P2: INDEXING PERFORMS AN UNBOUNDED WRITE AND
                          UNNECESSARILY LOADS EXISTING COLLECTION CONTENTS
--------------------------------------------------------------------------
Evidence:
- gemini_helpers.py:195–196: obtains existing IDs using unrestricted
  collection.get().
- gemini_helpers.py:209–230: creates complete arrays and makes one
  collection.add call.

Trigger:
A large document/chunk set or a large existing collection.

Impact:
Memory and latency grow with the full corpus; a single write can exceed the

SUBAGENT FINDING 17 — P2: LAMBDA ACCUMULATES INPUT PDFS IN /tmp WITHOUT

- ade_s3_handler.py:123–322: no corresponding temporary-file cleanup.
- lambda_helpers.py:213–224: does not configure ephemeral storage.

1. Public chat: existing session-local history and approved-public retrieval;
   no Supabase call unless a valid private-session cookie is present.
2. Explicit private-session start: same-origin POST, bounded request body,
   Turnstile challenge token, Supabase anonymous signup, and trusted Auth API
   identity verification. User metadata and locally decoded JWT claims never
   supply the authorization identity.
3. Browser receives an encrypted HttpOnly cookie, Secure under HTTPS and
   SameSite=Lax. Browser JS/UI state and LLM inputs receive no Auth JWT or
   refresh token. Private features require the top-level direct app URL rather
   than an embedded iframe that can block third-party cookies.
4. Each private callback decrypts/checks cookie expiry and Origin, asks Supabase
   Auth to verify identity, and queries only that owner's indexed memory row.
   Read responses are additionally checked for owner, shape, revision, and
   closed-session status before they can enter prompts or the memory panel.
5. Save: existing LLM summarization works on a copied own-memory snapshot.
   Extraction failure does not pretend to save. Validated data is written using
   a SECURITY INVOKER RPC deriving its owner from auth.uid(), with a revision
   compare-and-swap. Concurrent stale writers fail rather than overwrite data;
   the app does not automatically repeat non-idempotent writes or LLM extraction.
6. Forget: an atomic RPC scrubs personal fields and retains an irreversible
   closed marker. Closed identities cannot reopen by direct update, deletion,
   an initial revision-0 save, or a save already in flight. This avoids the real
   delete-then-recreate race discovered during implementation.
7. Return to public chat: clears local credentials and context even if storage
   is unavailable, without claiming remote deletion. Expired credentials cannot
   scrub remote memory; retention cleanup is explicit rather than falsely
   reporting that personal data was deleted.
8. Browser-session lifecycle guards use existing Gradio server-side State.
   Ending/switching/clearing a session invalidates pending outputs, including
   slow LLM replies and memory-panel refreshes. An old private response cannot
   repopulate a newer public session. Private saves are canceled if lifecycle
   changes occur during extraction. Public chat is preserved when opting in.
